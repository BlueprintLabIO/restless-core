# ADR 0012 — One identity issuer, two hosts

**Status:** Accepted (founders, 23 September 2026)

**Date:** 23 September 2026

**Parent:** [`ARCHITECTURE.md`](../../ARCHITECTURE.md) §7.4 ·
[ADR 0009](0009-provider-neutral-company-access-context.md) ·
[cross-layer contract §2.4](../specs/cross-layer-contract.md)

## Context

ADR 0009 made Core a relying party. Any issuer that proves a human, owns their membership and signs a
`CompanyAccessContext` can admit people to a company. Core verifies that context once, maps it to a
durable human Actor and honours signed removal. Core's side is built and shared by every deployment.

The issuer side now exists twice, and the two copies are drifting apart:

| | Self-hosted (`services/self-hosted-identity`, `1a55aff`) | Cloud (`restless-cloud` `fleet-web` + `fleet-api`) |
|---|---|---|
| Accounts | Better Auth 1.7.5, email + password | Better Auth ^1.7.2, plus passkey and 2FA |
| Membership | `organization` plugin, one fixed organisation | `organization` plugin, many organisations projected into Fleet |
| Handoff signing | Node, `jose`, key in `identity.json` | Rust `fleet-api/src/handoff.rs`, bound to a Fleet topology snapshot |
| `membership_version` | Constant: `1` on entry, `2` on removal | Durable `source_version`, advanced on every role or status change |
| Terminal controls | `removed` only | `suspended` and `removed` |
| Removal delivery | Synchronous POST. On failure it shows **Retry removal** | Durable `fleet_outbox`, lease-guarded reconciler, backoff, entry barrier |
| People screen | `public/app.js` on the accounts origin | `account/company/[organizationId]/people` in `fleet-web` |

Neither copy is visible from the company. The Core cockpit, which is the one company client, has no
members surface in any deployment. Local mode says nothing about why nobody can be invited. An existing
local-owner company can't turn on multiplayer: the self-hosted README says it "does not convert an
existing local-owner company". The reason is that first entry always creates a new `human-…` Actor
(`restless-orgintel/src/access.rs`), so the owner's history stays on the local `owner` Actor.

## Decision

**There is one issuer implementation, and each deployment hosts it.** Choosing an issuer host is the
only thing that differs between local Core, self-hosted multiplayer and Cloud. Company semantics,
cockpit surfaces and Core code paths stay the same.

### 1. The canonical issuer lives in Core, as a library with a thin host

`services/self-hosted-identity` becomes `services/identity`, a package with two parts:

- **The issuer library** (`src/issuer.mjs`, published as the dependency-free `@restless/issuer`)
  owns everything that must mean the same in every deployment:
  - who may change whom;
  - the membership admin API (section 3);
  - CORS to the company cockpit;
  - the issuer metadata document (section 4).
- **A host** owns its Better Auth instance, with the `organization` plugin and roles
  `owner | admin | member`, plus its account pages and the ports below. The self-hosted host is
  `self-hosted.mjs`, with Core's SQL Store: versioned membership, the handoff and control signer,
  and a durable control outbox. The Cloud host is `fleet-web`.

Core is the product that self-hosters install, so the canon lives in Core. The `restless-identity`
image carries the self-hosted service and the library at `/opt/restless/issuer`. Cloud copies the
library from that image by digest, the same way it consumes other Core artifacts.

Of the two current copies, Cloud's semantics are the better ones: versioned membership, suspend, and
outbox delivery with an entry barrier. Those move into the library. The self-hosted copy's shape is
the better one: small, single-purpose and colocated with Core. That shape is kept.

### 2. Three ports

| Port | What it answers | Self-hosted host | Cloud host |
|---|---|---|---|
| **Placement** | For one company: owner, plane, company and cell IDs, Core origin and host, entry readiness, and its organisation | Static values generated by `configure.mjs` | A query over Fleet's company, cell and plane tables |
| **Mail** | Deliver verification, reset and invitation messages, through the host's own Better Auth configuration | SMTP through Nodemailer | Cloud's mail adapter |
| **Store** | Membership state behind versioned entry and durable controls: read a viewer, list members, apply one authorised change | `membership-sql.mjs`: library tables, Ed25519 signer, outbox | Cloud's existing versioned controls, Fleet projection and Rust delivery |

**Amendment, 23 September 2026.** The first version of this ADR had two ports and put membership
storage inside the library. Implementing the Cloud host showed that Cloud's database enforces its
own membership invariants with triggers (`member_role_change_fails_closed`,
`member_delete_requires_removed_projection`, `member_identity_immutable`). Every role change and
removal must pass through Cloud's versioned controls and Fleet projection, which the Rust Fleet API
then delivers. The library therefore keeps what must mean the same everywhere and hands storage to
the host:
- who may change whom (`authorizeChange`), which each Store runs under its own lock;
- the admin API, CORS to the cockpit, and the metadata document.

This moves no company semantics into the issuer, and each host keeps exactly one membership truth.
Collapsing Cloud's store into `membership-sql.mjs` remains possible once its data and Rust delivery
are migrated. That is a separate decision.

Account security plugins (passkey, 2FA) belong to the host's Better Auth configuration. They are not
a port. Anything else that seems to need a port is a sign that company semantics are leaking into
the issuer (see Invariants).

### 3. The cockpit is the one members surface

Core adds **Company → Members**. Owners reach it with the other company settings; administrators
reach only this page.

- **Read side, from Core.** Humans bound to this company, with role, status, first and last entry,
  and the Actor they map to. The source is `human_principal_actor_bindings`, a verified projection
  Core already holds.
- **Write side, from the issuer.** Invite, cancel an invitation, change role, suspend and remove.
  The cockpit calls the issuer's membership admin API directly, using the issuer session the browser
  already holds because entry began there. The issuer authorises and writes. Changes reach Core only
  as fresh signed handoffs or signed controls. Core never relays admin calls. Relaying would make
  Core a delegate acting toward the issuer, a credential we otherwise don't need.
- **Pending invitations** are issuer state. The cockpit reads them from the issuer and never copies
  them into OrgIntel.

The issuer keeps only what must run on its own origin: sign-up, sign-in, verification, password
reset, account security, invitation acceptance and **Open company**. Its separate People screens
(`public/app.js`, and Cloud's `people` route) are deleted.

Credentialed cross-origin calls need the issuer and cockpit origins to be **same-site**, for example
`accounts.example.com` and `work.example.com`. Setup validates this and refuses otherwise. Each
host's CORS allowlist contains exactly the cockpit origins its Placement port returns.

### 4. Core probes the issuer; it never assumes one

The issuer publishes `/.well-known/restless-issuer`. It lists the contract version, admin API base,
supported roles, supported terminal statuses, invitation delivery (email or link only) and account
URL. Core fetches and bounds it with the JWKS client, and returns it with its verified members in
`GET /api/companies/{company}/members`. The cockpit shows only what the configured issuer actually
supports.

**Local mode is the null issuer.** It has one principal and no metadata document. Members then
shows the owner and one plain statement: this company is local-only, and inviting people needs
network entry, with the setup guide named in its explanation.

### 5. An existing company keeps its owner

Turning on network entry for a company that already has history is an explicit, one-time owner
claim. The first verified `owner`-role context binds to the existing local `owner` Actor instead of
creating a new human Actor, provided no principal has ever held the owner role or that Actor. The
claim is recorded as an Authority bootstrap fact (`owner_actor_claimed`, ARCHITECTURE.md #28) right
after the binding commits; a failure to record it is logged, not retried, and changes no access. A
second owner-role principal, or any non-owner role, gets a fresh Actor as today. A company whose
owner already entered before this change keeps that owner's human Actor. Going back from network
entry to local mode is not supported.

### 6. The organisation learns that someone joined

A human's first accepted entry writes one `daemon` → Exec message in the same transaction that
creates their Actor. Exec reads it in the owner's conversation scope and can give them a place in the
organisation: a Room, a responsibility, or a question to the owner about why they were invited. The
message grants nothing, and later entries send nothing. The owner claim sends nothing either.

## Invariants

1. The issuer never stores or receives company semantics: no Actors, Rooms, Work, organisational
   roles or Authority. Anything that needs company state belongs in Core.
2. Core never writes membership. Its binding table is a verified projection. A pending invitation
   does not exist in Core.
3. Membership role gates entry and cockpit surfaces only. It never grants capability or transfers
   root Authority, including through the owner claim in section 5.
4. There is one signer contract. A deployment that needs a different claim, audience or delivery
   rule changes the library and Core together, never one host.
5. All ADR 0009 invariants stand unchanged.

## Consequences

- Deletable in Core:
  - the self-hosted issuer's synchronous removal path and **Retry removal** state;
  - its constant membership versions;
  - its `public/app.js` People screen.
- Deletable in Cloud:
  - `fleet-api/src/handoff.rs`, `membership_control.rs` and `membership_control_reconciler.rs`, once
    the library outbox has carried a real removal;
  - the Better Auth membership hooks duplicated in `auth-core.ts`;
  - the `people` route.

  Fleet keeps placement, which is its real job.
- Cloud's handoff signing key moves from the Rust Fleet API to the Node host, unless founders
  choose a remote signer (Open questions).
- Self-hosted setup gains a same-site check and publishes the metadata document. Existing
  self-hosted installs need one migration of the removal table into the outbox.

## Risk dispositions

| Risk | Disposition | Reason |
|---|---|---|
| Issuer grows company semantics | **Invariant** | A second company brain is the failure ADR 0008 names. |
| Membership role becomes Authority | **Invariant** | Unchanged from ADR 0009. |
| Owner claim binds the wrong human to history | **Guarded** | One-time, owner-role only, recorded as an Authority fact, refused on repeat. |
| Cross-site placement breaks cookie-borne admin calls | **Guarded** | Setup refuses non-same-site origins. Cloud placement is checked in the first ticket. |
| Removal is delayed while Core is unreachable | **Accepted** | Entry is blocked at the issuer at once. The outbox retries until Core confirms. The live-session bound is ADR 0009's. |
| Library/host split adds a layer for one deployment | **Accepted** | Two hosts exist today. The split replaces a duplicate; it isn't speculative. |
| Better Auth version drift between hosts | **Accepted** | The library pins it, and Cloud inherits the pin through the release lock. |

## Resolved questions

1. **Cloud signing-key custody: the Node host holds it, with the library.** A remote signer would
   be a third port that exists only for Cloud, and invariant 4 forbids one host's signer differing
   from the other's. The self-hosted issuer already holds its key in a public-facing process, so this
   is the same posture in both hosts. The key is loaded from a mounted secret file, never from the
   environment. It rotates through JWKS `kid`, which Core already refreshes. **Accepted risk:** a
   compromised issuer process can mint entry, but only entry. Authority stays separate.
2. **Same-site placement: true by construction, with no fallback.** Company planes live
   under the account site's registrable domain (for example `account.<site>` and
   `<plane>.planes.<site>`). A cross-site fallback would be a second admin path that nobody uses.
   Because every plane then shares a site with the issuer:
   - issuer cookies use the `__Host-` prefix, so a sibling subdomain can't set or overwrite them;
   - admin endpoints require JSON bodies plus an exact `Origin` match;
   - owner-published company services are served from a **separate registrable domain**, never
     under `<site>`, the way GitHub serves user content from a separate domain. Otherwise
     company-authored content would be same-site with the accounts origin.
3. **Role changes: owner only.** Admins invite and remove *members*. Only the owner invites,
   promotes, demotes or removes an *admin*. This extends today's "only the owner can remove an
   administrator" rule and stops admins from creating more admins.
4. **Invitation delivery: email stays mandatory; a copied link is a convenience.** Without mail the
   issuer cannot verify an address. The copied link still requires sign-up with, and verification
   of, the invited address.
5. **First entry creates no owner Attention.** Exec receives the fact and raises Attention only when
   it needs the owner's judgement.
