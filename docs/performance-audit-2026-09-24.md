# Restless Core efficiency audit — 24 September 2026

This is a read-only audit of the local Restless plane and its current source. The goal is useful output per owner attention, elapsed time, compute, and model cost, as stated in `ARCHITECTURE.md`. A tenfold improvement across *all* those dimensions has not been measured and should not be promised from static inspection. The strongest opportunities differ by workload: idle companies, an open owner tab, an Exec wake, and a cold company boot.

## What was measured

- The host has 8 logical CPUs. A three-second `mpstat` sample at 10:13 AEST averaged 61.13% idle, so it was **not** saturated during this audit. An interval process sample showed Codex/ChatGPT and Docker VM processes alongside `restlessd-live`; attributing whole-host CPU to Restless would be wrong.
- Three company containers were running. In one `docker stats` snapshot, the main company used 1.965 GiB and 290 PIDs, Aris 507 MiB and 164 PIDs, and a `_test` company 527 MiB and 213 PIDs. Their CPU readings varied between snapshots; these are not stable idle baselines. The main container has a 4 GiB memory limit.
- The main company's current database has 15 Work rows, 0 Goal rows, and 2 Schedule rows. Authority has 106 `effect` records for it. The Authority records table as a whole is about 728 KiB. Full-history reads are therefore a **growth risk**, not an established current bottleneck.
- The browser broker's tab checkpoint in the main company changed modification time from `1790208745` to `1790208749` during a five-second observation while staying 2,225 bytes. This confirms repeated writes, but does not quantify disk wear or CPU cost.
- The local runtime image is about 6.63 GB and Docker reports 48.2 GB of image storage in total. Image layers are shared; the total is not an estimate of reclaimable space.
- The local company spend spools inspected for the main company and Aris are empty. This does **not** prove zero model usage: subscription/native routes and incomplete metering require different evidence.
- The repository's EXP-17 synthesis reports four bounded same-worker pairs at practical quality parity, with the explicit serial supervisory chain costing 77–194% more latency and 74–230% more spend (`docs/COORDINATION_THEORY.md:108-119`). This is an existing experiment on selected tasks, not a measurement of every current company workflow.
- No representative owner-page request trace, Exec turn latency distribution, model token-cost report, or database query plan was collected. Impact estimates below are hypotheses unless explicitly measured above.

## Ranked opportunities

For *productive* efficiency, the first decision is when another model should wake. The existing experiment shows that an extra reasoning layer can dominate cost even when local CPU is modest. The architecture already distinguishes a durable accountable lead from a model call on every transition; preserve that boundary while measuring whether routine commissioning and acceptance still cause avoidable wakes in real workflows. Batch ordinary successful completions, keep urgent contradiction/blockage wakes immediate, and compare accepted outcomes per dollar and hour with the same worker and tools. This is an empirical routing question, not a recommendation to remove accountability or weaken review.

## How to prove a 10x improvement

Choose one workload and a unit of value first. For **idle cost**, measure CPU-seconds, resident memory, PIDs, Docker subprocesses, checkpoint writes, and HTTP requests per company-hour with zero owner tabs and then one hidden tab. For **responsiveness**, time owner page navigation, conversation response, full doctor, Exec wake-to-first-output, and cold company ready state at p50/p95. For **productive efficiency**, record model requests, settled input/output tokens, elapsed time, owner interventions, and accepted artifacts per completed Work item. Separate uncertain metering from zero.

Run the same real workflow before and after each coherent change, with the same company size and active-tab state. A tenfold reduction in one background counter is plausible; a tenfold improvement in total product efficiency requires several of these costs to dominate the baseline and must be demonstrated end to end. Avoid adding benchmark fixtures that merely mirror implementation; use live-path smoke checks and existing exact telemetry.

No services, containers, source behavior, or live company data were changed during this audit. The pre-existing modification to `crates/restlessd/src/cell.rs` was not touched.
