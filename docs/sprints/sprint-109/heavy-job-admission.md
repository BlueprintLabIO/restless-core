# Heavy jobs and account capacity

Status: implementation and verification in progress; do not treat this as the full A0 resource gate.

Local burst jobs used to start immediately even when the account's existing workload admission reported memory pressure. They ran in the shared cgroup, but a new process could still compete with work already in that pool. The initial real-plane pressure probe reproduced that behavior: a job was `running` while the account admission reading said it was waiting.

The candidate saves a local job as a marked, unstarted Docker container and uses the existing scheduler to admit it. It reads the shared and company admission conditions without starting a Runtime; a stopped Runtime is not woken merely to run a queued job. It retains the intent across daemon restart, limits the pending queue to 64 per account scope using an Authority database advisory lock, and rejects a request that cannot fit even under the account's hard memory ceiling. Its capacity calculation conservatively reserves the full limits of already-running local jobs; this can reduce concurrency and needs real-work measurement. Remote jobs on a separately lent machine retain their existing path.

A two-company isolated test under the same account pool passed eight health, identity, Inbox and Work entry reads during application admission pressure. It checked an oversized refusal, the last queue slot under two simultaneous submissions, no source effect before admission, daemon restart, one effect after capacity returned, an untouched pre-upgrade created container, two companies' jobs sharing capacity, and company-destroy cleanup. The fixture removed its own containers, volumes and temporary pool. This is not a multi-owner Cloud test, a production walkthrough, a token or CPU savings measurement, or proof of every failure and lifecycle path. A0 remains open.

The job status shows `waiting_for_capacity` with a reason. Running and finished states keep their existing meaning. Completed containers remain available for the existing one-time status read. A queued job keeps its requesting actor; before launch the candidate locks that actor's source row against retirement. An inactive or missing actor leaves a durable failed receipt and its command is not started. An isolated test reproduced the earlier unsafe behavior, then passed with retirement before capacity returned. A real PostgreSQL test also verified that retirement waits for the start lease and that a retired actor cannot acquire a new lease. Failure handling and the complete release checks remain open.


A subsequent isolated test checked that an explicit owner stop persists across a daemon restart: the Runtime remained exited and the queued container remained created after capacity returned; an explicit start then allowed it to run. It also simulated Docker accepting creation while the confirmation timed out, and a failed rename: the unconfirmed preparations stayed inert. A transient status inspection failure returned an unavailable error instead of claiming the job was gone. These observations used the local candidate, not production. A repeat against daemon SHA-256 `028df8fe58da345a56233080a8933655d98af494ca64f85c30a9016b91eab716` also observed automatic reclamation after the real 120-second expiry and an accepted rename whose delayed response returned an ID; that job was tracked to success and its synthetic effect occurred once. The isolated test removed its own temporary pool and reported no cleanup problems.

The candidate does not establish end-to-end request idempotency when an accepted response is lost before the caller receives the job ID. The full resource gate remains open, including real multi-owner Cloud isolation, CPU pressure, equivalent-work efficiency and token measurements, and authenticated production checks.
