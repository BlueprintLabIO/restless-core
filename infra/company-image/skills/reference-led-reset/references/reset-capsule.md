# Reset Capsule contract

The capsule is a compact briefing artifact for a new Work node. It is not a design specification or a
dump of the prior attempt.

## Required fields

### Outcome

State what must be observably true when the new outcome is complete.

### Reset reason

Name the owner rejection or repeated drift in one to three factual sentences. Describe effects on the
outcome, not implementation repairs.

### Preserve

List accepted invariants, content, interfaces, authority boundaries and factual claims that survive
the reset.

### Source-of-truth hierarchy

Order exact sources. For each, state whether it governs identity, factual content, maturity,
interaction mechanics or another bounded concern.

### Exclude

Name candidate commits, branches, files, screenshots, conversations, stylistic directions and stale
instructions the producer must not inspect or receive.

### Clean base

Record the repository, exact reachable base commit, new Work id/worktree after commissioning, and the
expected integration branch if this is a final candidate.

### Native review

Name the exact routes, states, viewport profiles and user questions that must be operated and judged.
Include reduced motion and the full closing/footer state for visual websites.

### Owner decision

State the one accept/request-changes judgement the final ReviewTarget must support.

## Provenance check

Before the producer begins, the lead verifies:

- the new Work is not a revision of, dependent on, or based on a rejected producer Work;
- the effective Git base resolves to the capsule's clean commit;
- the generated worktree did not previously exist;
- bound artifacts are exactly the allow-listed references;
- no stale task-specific company mission contradicts the capsule; and
- the producer is Staff, while the accountable lead remains non-producing.

If any check fails, repair the commission before model work starts. A prompt that says “ignore it” is
not a substitute for a clean provenance boundary.
