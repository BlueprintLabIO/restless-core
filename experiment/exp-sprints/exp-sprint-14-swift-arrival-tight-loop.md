## Why the prior loop was loose

Three independent bottlenecks dominated:

- scripted gates proved mechanics but not whether a fresh player could understand and complete the
  route-end interaction;
- vision players spent large amounts of reasoning rediscovering processes, windows, focus, geometry
  and screenshots; and
- raw evidence grew into hundreds of frames and browser/runtime files rather than one decisive failure
  packet.

EXP-13 showed that durable observation/action can halve decisions and remove focus failures once the
correct target is attached. It also showed that attachment itself was not general: a browser launch
returned 10–14 ambiguous windows and no safe target identity.

## Three 10x hypotheses

### H1 — launch returns identity

Replace “launch, enumerate, guess, attach” with one ordinary Runtime operation that launches the
declared process group and returns an opaque handle for the exact new target surface.

The scratch tool may expose only:

- `launch`: start declared process roles and return the exact target handle;
- `observe`: return a fresh exact-target capture and health facts;
- `act`: perform a bounded input batch and return a resulting capture;
- `export`: write one compact immutable evidence manifest; and
- `stop`: explicitly stop the owned process group.

The launch manifest may contain target-specific commands and the intended process role. Target
identity, lifecycle, freshness and focus remain generic Runtime mechanics. The player must not infer a
window title. The tool is scratch Runtime code, not an Actor, Work type, daemon, database or OrgIntel
entity.

### H2 — cheap mechanics continuously, expensive judgement sparsely

Run fast deterministic mechanics gates on every candidate. Run a source-blind visual player only on a
material candidate that passes those gates. Stop at the first conclusive blocker, repair once, then
restart the fresh two-run acceptance gate. Deterministic tests never substitute for playability.

### H3 — one compact failure packet

Retain at most 12 decisive PNGs per native run plus one ordered action/result trace, exact candidate
identity, process/window receipts, terminal report and usage snapshot. Transient frames and Runtime
profiles stay outside Git and are deleted after adjudication. A failure packet must make the next
repair obvious without preserving an entire desktop session.

## Acceptance gates

### Product

- Two sequential fresh complete journeys with no human rescue.
- Route-zero on-foot unload visibly rejected.
- Deliberate drop and recovery succeeds.
- Early exit and natural seat re-entry remains usable.
- Route-end HUD, exit and unload affordance are visually coherent.
- Explicit delivery acknowledgement appears and host/client state agrees.
- No material collision or interaction blocker on the bounded path.

### Loop

- Player receives one opaque target handle and never lists or guesses window titles.
- Target survives model turns; explicit stop owns cleanup.
- First useful pixel is available without controller repair.
- Each run retains no more than 12 PNGs and one compact evidence manifest.
- Work-level start/end spend and elapsed time are recorded by the controller.
- A failed player report is sufficient for the producer to reproduce and repair the issue.

### Honesty

- Mechanics passes are not called playability.
- Model reports without direct pixels are invalid.
- Two completions do not prove fun, production readiness or Internet multiplayer.
- Founder taste remains a separate final judgement.

## Stop rules

Stop when:

- the exact candidate, model, image path, X11 input or clean-room boundary cannot be admitted;
- the same harness failure repeats twice;
- a second evidence-driven product repair still cannot restart the two-run gate;
- one player produces a conclusive blocker, until an allowed repair exists;
- the USD 60 ceiling is reached;
- evidence exceeds the compact retention contract without a named reason; or
- two fresh passes plus the bounded critique answer the sprint.
