# Experiment Sprint 01 — GPT-5.6 coordination frontier

**Status:** Ready for founder start signal. All experiment execution is paused.

**Decision owner:** Founder.

**Execution authority after the start signal:** the current Codex session may prepare and run only the isolated
experiments described here, update their evidence, and commit/push those experiment changes to `dev`.
Any material change to tasks, models, effects, evaluation or production architecture returns for
founder judgement.

## 1. Outcome

Produce an evidence-backed routing policy for when a strong GPT-5.6 accountable lead should:

- work alone;
- add one or more Staff producers;
- add an independent critic;
- use one of the proposed communication or shared-context mechanisms.

The sprint tests different kinds of work and different parts of Cosmon rather than repeatedly tuning
one game feature. It also includes non-coding sentinels so any conclusion can be scoped honestly.

The final deliverable is not “more agent machinery.” It is:

1. a compact decision frontier with native outcome evidence;
2. a final disposition for every proposed wildcard;
3. a measured team-size boundary wherever a team wins;
4. a systematic knowledge base that preserves counterevidence; and
5. deletion of mechanisms and harness paths that did not earn a production role.

## 3. Fixed decisions

These remain constant across all counted cognitive arms:

- Company structure is **Owner → continuously available Exec → one accountable lead per executable
  request**. Exec always delegates and returns to availability.
- `gpt-5.6-sol` is the accountable lead.
- `gpt-5.6-terra` is every Staff producer and independent critic.
- Free-provider availability is a separate runtime experiment and cannot contaminate coordination
  comparisons.
- Work records only genuine cross-actor responsibility; it is not the lead's thought graph.
- The lead owns canonical integration, native proof and the final decision.
- Elapsed time is an outer operating envelope, never semantic evidence that Work succeeded or failed.
- Observable process, artifact and callback events drive resumption. Missing evidence remains
  `unknown`.
- Every matched pair starts from the same immutable seed, uses the same task bytes and evaluator, and
  randomises arm order before execution.
- No experiment uses a live company or performs a consequential external effect.

## 4. Non-goals

- Building the Pokémon-like MMO itself as a production milestone.
- Optimising OpenRouter, ACP or free-provider routing inside this sprint.
- Exhaustively combining every model, task, team size and wildcard.
- Promoting an experimental candidate into the Cosmon source repository.
- Adding a universal deterministic team router before the evidence supports one.
- Treating token volume, test count or generated lines as outcome quality.

## 6. Work portfolio

Matched arms always use the same task. Different experiments rotate task type and game area to avoid
learning one scenario rather than coordination.

| Portfolio ID | Work type | Candidate task | Structural reason |
|---|---|---|---|
| G-UX | Coding/product UI | Field Atlas plus Squad Workshop | Two independently useful tools sharing one live roster source; genuine separability |
| G-SYS | Coupled gameplay systems | Battle AI/status interaction plus owner-visible feedback | High shared-state coupling and regression risk |
| G-WORLD | World/content | A bounded new habitat, traversal objective and authored encounter | Parallel content breadth with one integration point |
| G-PROG | Progression/product coherence | One evolution or boss progression slice spanning world, battle and UI | Tests causal-model coherence rather than file decomposition |
| G-REVIEW | Judgment/criticism | Blind native review of a playable candidate with planted and emergent defects | Tests whether independent criticism adds information |
| R-BREADTH | Sourced research | Decision memo from a frozen, inspectable corpus split into independent evidence regions | Intrinsically parallel non-coding breadth |
| D-CLEAN | Document/data | Player-facing field guide or release dossier with independently reviewable sections and one final synthesis | Clean component handoff outside code |
| O-TRACE | Operational investigation | Diagnose a frozen build/runtime incident from logs, repository state and rendered symptoms | Tool-heavy evidence gathering with no live effect |

Before activation, each task receives its own immutable scenario, seed locator, native target,
evaluator and negative control. The founder approves this portfolio, not unseen task wording: scenario
bytes may refine detail but may not change the structural role above without returning for approval.

Each experiment card also records the work shape below. Breadth comes from covering unresolved shapes,
not from running every task:

| Dimension | Recorded levels |
|---|---|
| Lead saturation | below, near or credibly beyond one effective lead session |
| Artifact separability | one coupled outcome, stable independent seams or parallel evidence breadth |
| Shared-state coupling | low, bounded interface or high shared causal state |
| Interface volatility | stable or one material dependency change |
| Epistemic uncertainty | explicit acceptance, open-ended synthesis or independent criticism |
| Tool/runtime density | low, environment-discovery-heavy or latency-overlappable |

A new task runs only when it resolves a live uncertainty on these dimensions or provides a required
cross-shape replication. Variety by itself is not evidence.

## 8. Wildcard mechanism programme

Every wildcard receives a final registry disposition, but not an automatic live run. An observed
failure code or unresolved routing question must activate it first. An activated wildcard receives the
cheapest bounded conformance/mechanism probe and, if mechanically viable, one live GPT-5.6 matched
comparison on the named task family. A failed mechanism stops before an expensive live pair; a first
live loss stops before replication. Absence of the trigger is recorded as `not-activated`, not dressed
up as a failed experiment.

At most two competing mechanisms may be screened for one measured bottleneck before an intermediate
choice. Broad coverage comes from work shapes and failure families, not from maximising mechanism count.

| ID | Mechanism | First task family | What it must beat |
|---|---|---|---|
| W01 | Session mitosis/shared-history fork | G-WORLD | Ordinary B1 briefing and reintegration cost |
| W02 | Fork–work–reunite cycles | G-WORLD with one interface change | One-shot W01 fork |
| W03 | Exec-to-lead lineage fork | Two simultaneous frozen department requests | Ordinary neutral Exec brief, without authority leakage |
| W04 | One brain, many hands | G-SYS or G-PROG | B0 and autonomous B1 on coupled work |
| W05 | Shared semantic blackboard | G-WORLD with shared interface | Ordinary messages, without becoming a second plan/database |
| W06 | Causal context deltas | Resume after two material and one irrelevant change | Full bounded context refresh |
| W07 | Proof-carrying handoff | G-UX Field Atlas handoff | Prose/callback handoff accuracy and integration time |
| W08 | Ambient artifact/interface events | G-UX or G-WORLD dependency change | Peer status messages and polling |
| W09 | Questions-only communication | One separable producer/integrator pair | Free-form B1 communication volume |
| W10 | Blind sibling diversification | Competing G-WORLD or research directions | Identical correlated siblings |
| W11 | Cross-finish | Two comparable creature/encounter components | Actors finishing their own branch |
| W12 | Micro-audition before ownership | G-PROG inspection/proposal probe | Fixed role assignment after including audition cost |
| W13 | Speculative sealed shadow | A task with two credible designs and one injected dead end | B0 recovery without shadow cost |
| W14 | Adaptive communication gates | Long independent work plus one real coupling event | Fixed rendezvous cadence |
| W15 | KV-state cloning or cached-prefix proxy | Long common game context, short divergent tasks | Transcript replay and ordinary prompt caching |
| W16 | Common room/private offices | G-WORLD kickoff, interface decision and final review | Continuous B1 communication |

Detailed hypotheses, risks and win signals remain in
[`coordination/PROGRAM.md`](../coordination/PROGRAM.md). This sprint document controls which task family,
model envelope and execution gates apply.

## 9. Execution waves

No wave begins until the previous wave's reports and registry changes are committed. Approval of this
sprint authorises progression through these gates without repeated founder approval when scope remains
unchanged.

| Wave | Work | Exit gate |
|---|---|---|
| 0 | Path/harness verification; E01 and E02 scenario freeze | Exact commands, hashes, negative controls and blind-review plan exist |
| 1 | E01 C-LH and E02 R-LH matched pairs | Ordinary frontier updated; provider/harness-invalid runs excluded |
| 2 | Diagnose E01/E02 churn; activate at most two primary candidates from W07/W04/W01/W09 | Selection cites observed failure codes; all unselected candidates remain unimplemented |
| 3 | Probe and live-screen the activated primary candidate(s) | Each activated candidate has `provisional-win`, `provisional-loss` or `blocked` |
| 4 | Select at most two dependent/secondary candidates from W02/W05/W06/W08/W10–W16 only if residual evidence demands them | Selection cites a remaining bottleneck that the primary screen did not resolve |
| 5 | Probe and live-screen only those activated dependent/secondary candidates | Same disposition; first losses stop and losing machinery is purged |
| 6 | Three-work-shape replication of provisional winners; E03/E04 only when triggered | Scoped winner and team-size evidence, or truthful absence of one |
| 7 | Routing synthesis, remaining wildcard dispositions, simplification and deletion | Final audit passes and no queued experiment lacks a recorded disposition |

Within a wave, arm order is frozen and randomised. Independent experiments may run concurrently only
when they do not share a mutable candidate, evaluator fixture, gateway or host resource whose
contention could alter the result.

## 10. Per-experiment protocol

1. Write the experiment card before implementation or execution.
2. Freeze task bytes, seed commit, task classification, models, tools, resource envelope and native
   acceptance target.
3. Obtain two independent pre-run workload classifications; retain disagreements.
4. Build and audit the evaluator; prove the negative control fails for the intended absent behavior.
5. Randomise and record arm order.
6. Run from fresh isolated worktrees. Do not inspect another arm.
7. Capture request-to-lead, first useful artifact, callback, accepted outcome and Exec-availability
   events.
8. Run native evaluation against the closed candidate, then blind review before producer narration.
9. Attribute failures with the stable taxonomy: specification, context, communication, integration,
   verification, runtime/provider or executive health.
10. Commit the immutable report, update the one registry row and change canon only when confidence or
    routing changes.
11. Purge a losing implementation before starting its dependent experiment.

## 11. Measurements

### Outcome

- native artifact acceptance and hidden evaluator result;
- severity-ranked defects and blind preference;
- owner-visible usability at the task's real review target;
- regressions in the unchanged game or source corpus.

### Time and computation

- request to lead ownership;
- first useful artifact and accepted final outcome;
- wall time and summed actor time;
- lead, Staff, critic, cached and newly processed tokens;
- tool calls and nominal compute cost even under a subscription plan.

### Coordination

- useful actor overlap and blocked time;
- briefing, questions, interface changes and terminal callbacks;
- redundant discovery and duplicated implementation;
- contribution accepted unchanged versus repaired or rejected;
- integration diff, conflicts, regression repair and lead replay;
- owner attention and Exec occupied time.

### Churn vector

- actor artifacts abandoned, discarded or substantially rewritten;
- lead work that duplicates Staff discovery or implementation;
- repeated reads, environment discovery and tool setup;
- messages, wakes and status turns that cause no material state change;
- retries, repairs and callback recovery attempts;
- integration rework, regression repair and evaluator reruns;
- completed useful work waiting unused for another actor.

Churn remains a vector with attributed failure codes, not one synthetic score. A mechanism must reduce
the relevant components without shifting equal or greater churn into quality loss, harness complexity
or owner attention.

No aggregate score may hide a materially worse outcome. Speed wins count only at non-inferior accepted
quality.

## 12. Invalid runs and stop rules

- Provider, credential or launcher failure before useful cognitive work: infrastructure-invalid.
- Harness revision that could change an arm's result: restart the matched set.
- Missing callback: `unknown`; preserve and expose workspace evidence, never infer success.
- Owner stop: retain evidence but do not count an unfinished comparison.
- Evaluator mutation or false proxy: evaluator-invalid; correct and restart both affected arms.
- First live wildcard loss: stop that branch; no replication.
- Provisional winner: replicate across three work shapes, including one non-coding task.
- Catastrophic authority, provenance or epistemic failure attributable to a mechanism: reject it even
  if it was fast.
- No B1 win: do not test larger teams.
- No observed trigger for a wildcard: mark it `not-activated`; do not build or run it.
- Neither E01 nor E02 shows credible unused parallel value or a coordination bottleneck: stop live
  wildcard work and retain the strong-lead prior.
- More than two plausible mechanisms for one bottleneck: rank by cheapest falsifier and screen no more
  than two before returning to the evidence.

The outer run envelope protects host resources. It does not decide whether an actor or Work has
semantically failed.

## 13. Risks and dispositions

| Risk | Disposition |
|---|---|
| Repeating provider experiments instead of coordination work | Invariant: GPT-5.6-only cognitive envelope; provider study separate |
| Overfitting to one game feature | Guarded: rotate systems, world/content, UX, progression and review tasks |
| Artificial decomposition makes teams look useful | Guarded: delegated outputs must be independently valuable and reviewable |
| Strong lead completes the whole task before Staff contributes | Accepted evidence about the crossover; do not enlarge scope mid-run |
| Callback ceremony loses a completed artifact | Guarded: preserve exact workspace evidence and classify `unknown`; W07 measures the alternative |
| Shared history correlates errors or leaks authority | Guarded: blind review, role/tool divergence and redaction audit |
| Harness complexity becomes the product | Guarded: implementation-complexity measurement and post-wave deletion |
| Experimental game code leaks into product history | Invariant: isolated seed worktrees and no product promotion |
| Test volume consumes excessive compute | Guarded: one smallest falsifying probe, one live screen, replication only for winners |
| Interrupted run is narrated into a result | Invariant: only closed matched arms with native evaluation count |
| The wildcard catalogue becomes an execution checklist | Guarded: observed failure activation, at most two candidates per bottleneck, and `not-activated` as a valid final disposition |

## 14. Sprint acceptance criteria

The sprint is complete only when all are true:

1. E01 and E02 have valid matched B0/B1 results, or a specific external feasibility block is recorded.
2. E03 and E04 have run exactly when their trigger fired, and otherwise record why they did not.
3. Every W01–W16 row has a committed final disposition. Every evidence-activated and mechanically
   viable wildcard has one live matched GPT-5.6 comparison; absent triggers are `not-activated`.
4. Every provisional winner has three order-randomised replications across distinct work shapes,
   including one non-coding task and one independent model session for review.
5. Team size is measured only on an ordinary or wildcard team winner.
6. Evidence spans G-UX, R-BREADTH and at least one materially different G-SYS/G-WORLD/G-PROG task;
   D-CLEAN/O-TRACE runs only when it resolves an untested work-shape or replication requirement.
7. Exec dispatch/availability remains proved and unchanged in every organisation.
8. The final routing policy states “use when / avoid when,” confidence, counterevidence and falsifier.
9. Losing mechanism code and duplicate communication paths are deleted; reusable probes remain.
10. `coordination/CANON.md`, `REGISTRY.md` and `EVIDENCE.md` agree with all immutable run reports.
11. A final fresh-context audit reproduces the claimed evidence and finds no queued experiment without
    disposition.
12. `dev` is clean, pushed and contains no generated run databases, model homes, credentials or
    candidate worktrees.
