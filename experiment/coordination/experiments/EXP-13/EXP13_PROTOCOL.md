# EXP-13 frozen execution protocol

The approved experiment contract is
`/company/reference/exp-sprint-13-durable-visual-operator-frontier.md`. This file is the concise
execution contract inside the isolated company.

## Outcome

Choose one terminal disposition from:

- `thin-operator-supported`
- `playbook-sufficient`
- `temporal-extension-supported`
- `model-or-policy-limited`
- `infrastructure-invalid`
- `human-profile-not-supported`
- `inconclusive`

The lead must support the decision with native outcomes, clean-room reports, cost, invalid attempts
and exact artifact locators. No aggregate score may conceal a domain failure.

## Organisation

1. Exec appoints one non-producing Experiment lead, gives it this protocol and returns.
2. The lead commissions one infrastructure Staff worker to prepare the B1 skill and B2 scratch
   operator from `/company/reference/operator-interface.md`.
3. Each evaluated arm is owned by a fresh visual-player Staff process. No player receives another
   arm's findings, source, expected defects, producer reasoning or deterministic oracle.
4. One independent adjudicator compares reports after the arms are terminal. It does not edit tools
   or product artifacts.
5. If Wave 3 activates, one separate producing Staff actor repairs exactly one accepted issue and a
   fresh player verifies it.

Staff identities may be reused across sequential Work only when the model process and native target
are demonstrably fresh and its context excludes other-arm evidence. Prefer distinct actors where that
is cheaper to prove.

## Candidate arms

### B0 current loop

Use `xdotool`, `scrot`, process commands and OMP image reads directly. The player assembles target
identity, focus, geometry, action/capture and evidence itself. Do not expose the B1 skill or B2 tool.

Run only on G1.

### B1 playbook only

Use the same ordinary tools plus `/company/skills/visual-operation/SKILL.md`. Do not use
`visual-operator` or read its implementation.

### B2 thin operator

Use the B1 behavioural guidance plus the scratch `visual-operator` implementation. The only intended
surface is:

```text
visual-operator attach
visual-operator observe
visual-operator act
visual-operator export
```

The tool owns target/process continuity, exact visible-surface identity, calibrated input, atomic
resulting captures and the mechanical evidence manifest. The player still owns every action choice,
observation, inference, severity and verdict.

### B3 conditional temporal extension

Do not build or run by default. Activate one replay only when a B2 report identifies a material fact
lost between still captures and the short retained frame/event history would directly contain it.

## Wave 0

- Verify exact Terra model and image path inside the company.
- Record exact checksums for all targets.
- Confirm one shared USD 120 company ceiling covers all actors and Work.
- Admit Godot, Chromium, Gnumeric or another native spreadsheet application, X11 input and exact
  region capture.
- Make player-visible targets read-only; give each arm a distinct writable evidence root.
- Freeze reset commands and player prompts before any arm begins.

## Wave 1: G1 gate

Use `/company/scenarios/G1.md`. Run B0, B1 and B2 in the frozen controller order recorded at Wave 0.
Every run starts fresh host/client processes and a fresh model process. A valid report contains direct
image observations, ordered actions, resulting states, target identity, uncertainty and a terminal
verdict.

Continue only if B2 materially beats B1 on native progress, recovery, accepted feedback, invalid
interaction, manual rescue or cost. If B1 matches B2, select `playbook-sufficient`, purge B2 and stop.
If neither improves B0, classify the observed model, policy or infrastructure limit and stop.

## Wave 2: generalisation

Only after the G1 continuation gate, run B1 and B2 on `/company/scenarios/W1.md` and
`/company/scenarios/D1.md`. Target-specific launch and calibration may be configured, but the operator
implementation may not be redesigned for each application.

The website is a read-only frozen build. The desktop CSV is labelled test data; its hidden expected
copy may be read only by the deterministic verifier after the visual player finishes.

## Wave 3: one closed repair loop

Select one material G1 or W1 issue from the winning shape. The lead accepts or rejects the report from
native evidence. If accepted, commission one producer to repair it in a new isolated writable copy.
Run the project's exact checks, then give a fresh player only the repaired native target and original
public goal. Require independent reproduction of the old path and confirmation or rejection of the
repair.

Stop after this one loop. This is not another open-ended product build.

## Human-reference boundary

The files under `/company/reference/human-signals` are historical founder observations against prior
revisions. They are useful product history but are not matched human-reference runs for these frozen
targets. No model may re-label them as matched data or impersonate a human. Report the five human
profile dimensions as unavailable or unsupported unless an actual new human trace appears.

## Measurement and stop

Record per arm:

- native checkpoints and outcome;
- accepted, rejected, false-positive and duplicate findings;
- independent reproduction result;
- decisions, observations, actions and captures;
- stale capture, wrong-window, focus, coordinate and target-loss failures;
- harness invalid attempts and restarts;
- cost and wall time;
- owner/controller interventions; and
- evidence bundle completeness.

Stop on the first decisive disposition, any USD ceiling, clean-room contamination, two repeats of one
harness failure without new evidence, an unavailable native dependency, or a requested external
effect. Preserve the evidence and remain quiet.
